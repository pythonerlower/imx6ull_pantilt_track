# 云台控制与视频链路协议（3B 冻结）

本文件是**规范性**的。C 侧权威实现是
`imx6ull_project_src/common/proto/pantilt_proto.h`，Python 侧镜像在
`imx6ull_project_src/pc/tracker/ptproto.py`。二者不一致时以本文件为准，
然后两边一起改——`scripts/proto_selftest.sh` 会逐字节比对两边的编码，
不一致就失败。

冻结日期 2026-10-07（里程碑 3B）。改动规则见文末「版本与兼容」。

## 1. 通则

- **字节序**：全部小端（LE）。
- **不许把 C 结构体直接当网络载荷**。内存里的 struct 是便利容器，编译器会
  按对齐插填充字节：`timestamp_us` 是 u64、在 `ptp_ctrl` 里落在偏移 12 上，
  编译器要在它前面补 4 字节，于是 `sizeof(struct ptp_ctrl)` 实测是 **40**
  而不是线上格式的 32；`ptp_video_hdr` 同理是 40 比 36。**线上格式只由
  写出顺序定义**。也不要 `memcmp` 整个结构体比较——填充区的内容未定义。
- **魔数 + 版本**：每个包类型各有 4 字节魔数，另有 2 字节版本号
  （当前 `PTP_VERSION = 1`）。串端口、旧固件、协议漂移都会被这两样挡下。
- **端口**：
  | 用途 | 端口 | 方向 |
  |---|---|---|
  | 控制 | 9100 | PC → 板端 |
  | 遥测 | 9101 | 板端 → PC |
  | 视频 | 9200 | 板端 → PC |

## 2. 控制包 PC → 板端（32 字节）

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 4 | `magic` | `0x31544350`（`'PCT1'`） |
| 4 | 2 | `version` | 1 |
| 6 | 2 | `mode` | 见下表 |
| 8 | 4 | `seq` | 单调递增，客户端判重用 |
| 12 | 8 | `timestamp_us` | **PC 单调时钟**，微秒 |
| 20 | 4 | `flags` | bit0 = 心跳标记 |
| 24 | 2 | `pan_tick` | 绝对目标 tick |
| 26 | 2 | `tilt_tick` | 绝对目标 tick |
| 28 | 4 | `crc32` | 覆盖字节 0..27 |

模式：

| 值 | 名称 | 语义 |
|---|---|---|
| 1 | `MANUAL` | `pan_tick`/`tilt_tick` 当绝对目标 |
| 2 | `TRACK` | 同 MANUAL；第一版仅标签不同 |
| 3 | `HOME` | 回 home，**忽略** tick |
| 4 | `STOP` | 停止爬升并保持当前位置，**忽略** tick |
| 5 | `HOLD` | 同 STOP；供上位机显式表达「按住别动」 |

`flags` bit0（`PTP_FLAG_HEARTBEAT`）：置位表示「这一包的目标与上一包相同」。
**板端不依赖该位判重**——它按 `(mode, pan_tick, tilt_tick)` 的值去重，所以
客户端漏置标志也不会污染驱动的命令计数。该位只用于遥测统计。

### 2.1 时间戳不是墙钟

板端**不能**用它和本机时钟比较，两者不同源（PC 是开机后的单调时间，板端
另有自己的计数器）。板端只检查**单调性**：新包的 `timestamp_us` 必须严格
大于上一条被接受包的值，否则记 `rej_stale` 并拒收。这条能挡住 UDP 乱序里
迟到的旧包，但**不能**用来判断「客户端是不是已经卡住了」——那是看门狗的事。

### 2.2 板端校验顺序（每一类各自计数）

1. 长度/CRC 不符 → `rej_crc`
2. 魔数不符 → `rej_crc`（串端口的典型症状）
3. 版本不符 → `rej_crc`
4. `seq` 不前进（重复或倒退）→ `rej_seq`，**除非**连续倒退超过
   `SEQ_RESYNC_MS = 1000 ms`，那时判定为客户端换了一茬（PC 重启后其单调
   时钟归零，`seq` 会大幅倒退），接受该包并重置会话
5. `timestamp_us` 不前进 → `rej_stale`
6. 模式非法 → `rej_mode`
7. `MANUAL`/`TRACK` 且 tick 越出 `safe_min..safe_max` → `rej_range`

第 4 条的逃生门是必需的：没有它，PC 重启后 daemon 会**永久失聪**——表现是
「云台再也不动，而两端都显示正常」，极难排查。反过来，逃生门只是逃生门：
第一个乱序包仍然要被拒（早期实现把它写成了接受的旁路，已被
`pc/tracker/test_plane.py` 的用例逮住）。

第 7 条意味着**越界在 daemon 就被拦下，不指望驱动钳位兜底**。驱动当然也会
钳位（那才是最终权威），但那样 `clamp_low`/`clamp_high` 会被无意义的请求
刷屏，真正的越界事故就淹没在噪声里了。

|---|---|---|---|
| 0 | 4 | `magic` | `0x31544550`（`'PET1'`） |
| 4 | 2 | `version` | 1 |
| 6 | 2 | `drv_status` | 0 UNINIT / 1 READY / 2 SLEW / 3 HOLD |
| 8 | 4 | `seq` | 板端计数，丢包可查 |

| 24 | 2 | `wd_ms` | 驱动侧看门狗 |
| 26 | 2 | `daemon_wd_ms` | daemon 侧看门狗 |
| 28 | 2 | `pan_cur` | 驱动认为的当前 tick |
| 30 | 2 | `tilt_cur` | |
| 32 | 2 | `pan_tgt` | 当前目标 tick |
| 34 | 2 | `tilt_tgt` | |
| 36 | 2 | `pan_home` | |
| 38 | 2 | `tilt_home` | |
| 40 | 2 | `pan_safe_min` | |
| 42 | 2 | `pan_safe_max` | |
| 44 | 2 | `tilt_safe_min` | |
| 46 | 2 | `tilt_safe_max` | |
| 48 | 4 | `ms_since_ctrl` | 距最后一条被接受的控制包 |
| 52 | 4 | `last_latency_us` | 命令到首次写出 PWM 的耗时 |
| 56 | 4 | `cmd_count` | |
| 60 | 4 | `clamp_low_pan` | |
| 64 | 4 | `clamp_low_tilt` | |
| 68 | 4 | `clamp_high_pan` | |
| 72 | 4 | `clamp_high_tilt` | |
| 76 | 4 | `i2c_err` | |
| 80 | 4 | `watchdog_trips` | 驱动侧触发次数 |
| 84 | 4 | `ctrl_rx_ok` | daemon 接受的控制包数 |
| 88 | 4 | `rej_crc` | |
| 92 | 4 | `rej_seq` | |
| 96 | 4 | `rej_stale` | |
| 100 | 4 | `rej_mode` | |
| 104 | 4 | `rej_range` | |
| 108 | 4 | `daemon_wd_trips` | daemon 侧触发次数 |
| 112 | 16 | `reserved[4]` | 见下 |

**计数一律取低 32 位。** 驱动里的计数是 `__u64`，遥测带宽比绝对精度值钱，
这些计数按秒级累加，32 位要跑很久才回绕；PC 端按 u32 无符号解读。

`reserved[0]` 目前回传 **`session_resets`**（因 seq 持续倒退而重置会话的
次数，见 §2.2 第 4 条）。

`reserved[1]` 定义为 **振动事件**（Phase 7，2026-10-08）：

| 位 | 名称 | 语义 |
| --- | --- | --- |
| 31:16 | `ev_count` | 事件**累计计数**，板端收到一个事件加一 |
| 15:0 | `ev_age_ms` | 距最近一次事件的毫秒数；`0xFFFF` = **从来没有过** |

- **PC 端判计数上升沿**，不要用"计数值"当事件数（16 位会回绕，重启后归零）。
  首帧只记录计数、不触发——否则刚起来的进程会拿板端的历史计数凭空动作一次。
- 之所以是"计数 + 年龄"而不是一个锁存位：锁存位丢掉在同一个遥测周期内发生的第二个事件，
  而年龄字段让 PC 端能直接判新鲜度（`ev_age_ms < 锁存窗口`），不必依赖"置位时长"。
- **不是 WoM 硬件中断**。M1 探测证明 ICM20608 的 INT 脚在本板接不出中断
  （见 `logs/phase7/m1_icm_int_probe_20261008.md`），板端走的是**软件阈值**
  （`securityd --vib-thr-mg`，默认 0 = 关闭）。协议这一层只传"有没有事件"，
  不关心它从哪来。
- **来源**：`securityd` 经本地 UNIX 数据报给出（ABI 在 `common/proto/security_event.h`），
  daemon **锁存 2 s** 后编码进本字段。`pantilt_daemon` 自己**不读传感器**。
- 其余两个（`reserved[2]`、`reserved[3]`）保留。加新字段前必须确认用户态兼容。

**启用预留字段算不算破坏"3B 冻结"**：不算——老客户端按保留字段忽略它，行为不变；
**只有已定义字段的偏移或语义变更**才算破冻结，那类改动必须走版本号提升。
新客户端遇到全 0 必须理解为"无事件"（不是"没这个字段"）。

### 3.1 遥测发到哪儿

默认回发给**最近一条控制包的源 IP 的 9101 端口**——注意是源 IP、不是源端口。
客户端的控制 socket 通常绑在临时端口上，而它收遥测用的是绑在 9101 的
`TelemReceiver`；照源端口回发的话遥测会全部落到没人监听的端口上，症状是
「控制正常、遥测一条都收不到」。`--telem-dst HOST:PORT` 可固定到别处。

## 4. 视频分包 板端 → PC（1400 + 36 字节）

一帧 YUYV 320×240 = 153600 B，按 1400 B 切片，共 110 片。每片一个独立 UDP
报文，各自带完整头部（1436 B < MTU 1500）。

| 偏移 | 长度 | 字段 |
|---|---|---|
| 0 | 4 | `magic` = `0x31565650`（`'PVV1'`） |
| 4 | 2 | `version` = 1 |
| 6 | 2 | `chunk_idx` | 从 0 开始 |
| 8 | 2 | `chunk_total` | 本帧总片数 |
| 10 | 2 | `payload_len` | 末片可小于 1400 |
| 12 | 4 | `frame_id` | 每帧 +1 |
| 16 | 8 | `timestamp_us` | 板端单调时钟，抓帧时刻 |
| 24 | 2 | `width` | |
| 26 | 2 | `height` | |
| 28 | 2 | `format` | 1 = YUYV，2 = MJPEG |
| 30 | 2 | `flags` | bit0 = `SINGLE`（整帧只占一片） |
| 32 | 4 | `crc32` | **只覆盖载荷** |
| 36 | ≤1400 | payload | 紧接着头部 |

CRC **只覆盖载荷、不覆盖头**：头里的 `frame_id`/`chunk_idx` 本来就是用来
发现乱序与缺片的；把它们也算进 CRC 会让「哪一片坏了」变成「整个头都不可信」，
反而丢掉了定位信息。

接收端必须先按**声明的 `payload_len`**核对实际长度，再算 CRC。少了这一步，
切片越界会被静默截断到「恰好剩下的字节」，于是 CRC 在某些取值下碰巧算对，
把错误长度当成合法包放过去。

`payload_len` 与 `chunk_total` 都是 u16，故单帧上限 1400 × 65535 ≈ 91 MB，
对本项目（单帧 153600 B）绰绰有余。

重组规则（`pc/tracker/video_rx.py`）：同 `frame_id` 的片按 `chunk_idx` 归位；
重复片计 `dup_chunks`；`idx` 小于本帧已收到的最大 `idx` 计 `reorder_chunks`；
只给出**完整帧**；帧号跳号计入 `frames_lost`；窗口外的缺失帧被放弃并计入
`frames_incomplete`。

**`frames_lost` 是跳号数，不是「丢了」的帧数。** 板端 `frame_id` 取自 V4L2 的
`buf.sequence`（每 DQBUF 一帧加一），所以号段缺口只有三种成因，而接收端
**无法**区分它们是哪一种：

| 成因 | 谁能分辨 |
|---|---|
| 板端 `--fps` 主动节流丢弃（板端 `节流丢` 计数） | 只有板端 `[stats]` |
| 板端环缓冲被覆盖（板端 `覆盖丢` 计数） | 只有板端 `[stats]` |
| 整帧的所有分片都丢在网络里（板端 `采集/入环/出环` 对得上，接收端凭空少一帧） | 对比板端 `[stats]` |

所以两侧统计的字面量分别叫「跳号」和「整帧丢失」之外的词——把第一种说成
「丢失」会读成故障。要对账时，拿板端 `[stats]` 的
`采集 = 节流丢 + 入环` 两条恒等式去比，缺的那一段才是真丢包。

**帧一旦结算就不再重建。** 这是 2026-10-07 修的一条计数缺陷：帧结算后
`_pending` 里就没有它了，此时它迟到的复制包会被当成「新帧」重新建槽，随即又被
窗口判为残缺帧结算掉，于是同一个 `frame_id` 被反复结算成残缺。板端实测撞到过：
板端只发了 580 帧，接收端报 580 完整 + 193 残缺——那 193 全是复活出来的，
`frames_incomplete` 与 `chunk_loss_pct` 因此虚高。现在记过的帧号（`_settled`）
一律不再重建，这类迟到片单列 `late_chunks`，与窗口内的 `dup_chunks` 分开——
前者量链路的多路径复制，后者量传输中的重传/复制，混在一起看不出是哪一种。

`late_chunks` 是判断链路是否有**多路径复制**的直接指标（见 §9 第 3 项）：
它的值接近 `dup_chunks` 甚至远超时，说明包被复制到了「整帧都交付完了还继续来」
的程度，而不是偶尔重发。

## 4.1 CRC 由 zlib 实现

PC 侧的 `crc32()` 直接调 `zlib.crc32`，**不是**自实现的逐位循环（2026-10-07 改）。
原来那份逐位循环在环回基准里占 `recv_frame` 总耗时的 93.8%（2407 µs/包），把接收
上限压到 306 pkt/s，而 320×240@15fps 需要 1650 pkt/s——瓶颈在 PC 侧，链路修得再
干净也收不到完整帧。`zlib.crc32` 是同一算法的 C 实现，快 2200 倍。

「两侧独立实现才算对拍」这个动机不成立：`scripts/proto_selftest.sh` 是拿 C 的
`ptp_crc32` 与 Python 侧比，zlib 与手写循环本就是两份独立实现；`ptproto._check_layout`
里仍钉着标准 check value `0xCBF43926`。改后 C↔Python 三份报文（ctrl/telem/video）
仍逐字节一致，`video` 向量的 CRC 字段就在被比较的字节里。

## 5. 心跳、看门狗与 KEEPALIVE

**客户端必须恒定发心跳，不能「有变化才发」。** 板端看门狗只看「距最后一条
被接受的控制包多久」，不看值有没有变；静止三秒不发就会被接管。

两级看门狗，兜的不是同一件事：

| 层 | 阈值 | 触发后 | 兜的是 |
|---|---|---|---|
| daemon | 500 ms 无控制包 | 下发 `STOP` 保持位置，状态转 `LOST` | 上位机没了 |
| 驱动 | 1500 ms 无 KEEPALIVE/新目标 | 中止爬升进 `HOLD` | daemon 自己死了 |

**续命与下达目标是两个不同的动作。** 驱动新增了 `PANTILT_IOC_KEEPALIVE`
（`_IO(magic, 0x06)`），它**只把看门狗截止时刻往后推**，不碰
`status`/目标/爬升定时器。为什么不能用「重复下发同一个 `SET_TARGET`」代替：
`SET_TARGET` 是无条件的副作用集合，会 `++cmd_count`、把 `status` 强制回
`SLEW`、并重排爬升定时器（每步最多推迟一个 `slew_ms`，约慢 10%）。

于是 daemon 的规则是：

- 每拍（默认 20 Hz）→ `KEEPALIVE`
- 目标 `(mode, pan, tilt)` 变化时 → `SET_TARGET`
- **或者驱动报 `HOLD` 时** → 重新下发 `SET_TARGET`

最后一条不能省：驱动看门狗触发后必须由用户态**再次下发**才恢复，否则会出现
「客户端目标没变、云台却永久停住」。

### 5.1 一次性命令能走多远

`watchdog_ms / slew_ms` 就是**单条命令能走的最大 tick 数**（默认
1500 / 20 = 75）。只发一条 `SET_TARGET` 然后不管，走满这个数就会被看门狗
掐断。手动一次性下发（如 `pantilt_ctl target`）必须相应调大 `--watchdog`，
或者像 `pantilt_daemon` 那样持续续命。

## 6. 怎么保证两端真的对上

三层，缺一不可：

1. **编译期**：`pantilt_proto.h` 里的 `_Static_assert` 锁死三个长度
   （32/128/36）。改字段忘了同步时先炸在这里。
2. **逐字节比对**：`scripts/proto_selftest.sh` 用同一组向量分别跑
   `user/video_link/test_proto.c`（C）和 `pc/tracker/selftest_vectors.py`
   （Python），`diff` 两边的十六进制串。C 侧编码器与 Python 侧解码器由此
   被传递性地钉在一起。
3. **行为级**：`pc/tracker/test_plane.py` 用 `--fake-driver` 起真实 daemon
   进程，配真实 `ControlClient`/`TelemReceiver` 走 UDP 环回，验证校验顺序、
   去重、看门狗、HOLD 解除等语义。

第 2 层用向量而不是"读代码",是因为端序/偏移这类错误在两边各自看都像对的。

## 7. 版本与兼容

- `PTP_VERSION` 只在**破坏性改动**时 +1：改字段偏移、含义、或删字段。
  加字段用 `reserved`，不算破坏性。
- 收到未知版本一律拒收并计数，不猜测语义。
- 改本文件时必须同步：`pantilt_proto.h`（C 权威）、`ptproto.py`（Python 镜像）、
  两边的向量文件，然后跑 `scripts/proto_selftest.sh` 与 `make test`。
