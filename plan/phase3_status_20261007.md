## 2. 视频链路：三个独立问题

**它们是叠加的，互相掩盖**——任何一个单独存在都足以让视频收不到完整帧。
按发现顺序记，但按严重度排序的话 **B 最致命**。

### A. 链路三倍复制（Windows 宿主机，不在本仓库内）

**现象**：板端 `eth0` TX 包增量恒等于 `video_link` 的 `sendto` 次数，板端只发一次；
PC 内核收到的唯一包数正好是 3 倍（唯一 22550 → 收到 67382），100% 唯一交付、内核零错误。

**根因**：宿主机上 **ICS 把 WLAN 共享给以太网**，而**同一块以太网卡**
（Realtek USB GbE，`00-E0-4C-05-2C-88`）**又被 VMware 桥接（vmnet0）给 `ens38`**。
两条路径压在同一张网卡上，同一份上行包各送一次。

配置级证据（`HNetCfg.HNetShare`）：

```
WLAN                                Sharing=True   Type=0   <- Public（出口）
以太网                               Sharing=True   Type=1   <- Private（下游，同时被桥接）
IPEnableRouter = 0                  <- 不是 RRAS 那套，纯粹是 ICS 的 NAT，改它不需要重启
```

**代价**：链路占用从 5.4× 余量掉到约 1.8×。

### B. PC 侧 CRC 是纯 Python 逐位循环（真正的阻塞点，已修）

`ptproto.crc32()` 原来每包跑 11200 次解释器循环。

| 指标 | 值 |
| --- | --- |
| `crc32` 占 `recv_frame` 总耗时 | **93.8%**（2407 µs/包） |
| 环回实测：裸 `recvfrom` | 56512 pkt/s |
| 环回实测：`VideoReceiver` | **306 pkt/s** |
| **需求**（110 片 × 15 fps） | **1650 pkt/s** |

上限比需求低 5 倍——**A 修好了也照样一帧收不全**。换成 `zlib.crc32` 后
**20789 pkt/s**（12.6× 余量）。

### C. 已结算帧被迟到复制包"复活"（计数污染，已修）

A 的第三份复制常在整帧交付完才到，原代码把它当"新帧"重建槽位，随即被窗口判为
残缺帧结算掉。实测形态：**板端只发了 580 帧，接收端报 580 完整 + 193 残缺**
（`片丢 23.89%` 也是这么虚高出来的）。这是**计数**错误、不是交付错误，
肉眼审代码看不出来。

**已决（2026-10-07）**：`video_link --fps` 当初不生效的根因是它只送进
`VIDIOC_S_PARM`——**向传感器请求帧率**而非输出限速，而 OV5640 只接受离散档位
（15 受理、20 报 EINVAL、5 受理但写回 15）。现在改成**输出目标帧率**：
`DQBUF` 之后整数分频丢帧，不进 Ring Buffer、不上网。默认值 15 时每帧放行，
行为与旧版一致。详见 §6 第 3 项与
[`logs/phase3/20261007_fps_ab_acceptance.md`](../logs/phase3/20261007_fps_ab_acceptance.md)。

## 8. `main.py` 被清空事故（2026-10-07 14:13）—— 低级失误，只留教训

为验证一个突变体（M7），在 `imx6ull_project_src/pc/tracker/` 下执行了一条就地改写：

```python
open("main.py","w").write(open("main.py").read().replace(old, new, 1))
```

**Python 先求值写入目标 `open("main.py","w")`，才轮到右边的 `read()`** —— 文件先被
截断成 0 字节，右边读到空串，写回的也是空串。`main.py`（2305 行 / 115 KB，`Manual` /
`Auto` / `SignProbe` / `LashProbe` / `run_video` / CLI 全在里面，**从未进过版本库**）
当场归零，整个 tracker 不可运行。

**已恢复**：拿突变脚本顺手 `cp` 出来的 `/tmp/main.py.bak`（13:42 的真实中间态）作检查点，
把 `Edit` 流与 `Bash heredoc` 流两条改动线按真实时间戳交织重放，63 步全部匹配。
验收：`ast.parse` OK、`main.py --help` rc=0、CLI 校验冒烟 7 条全对、
`test_auto.py` 与 `make test-unit` 全绿。

⚠️ **恢复件与清空前的原件无法逐字节比对**（当时没有任何完整备份），只能保证**行为**
一致，注释/措辞未必。跑实机若见与预期不符的行为，**先怀疑这一点**。

**教训（就这四条）**
1. **就地改文件一律走临时文件** —— 写 `.tmp` 再 `os.replace()`，或先 `cp` 备份再用
   `sed -i` 那类"先读后写"的工具。**永远不要写 `open(f,"w").write(open(f).read()…)`。**
2. 一次性验证/突变脚本，动手前先落一份带时间戳的备份。
3. 不要用"另一条类似命令是安全的"推断这条也安全 —— 逐条看求值顺序。
4. 仓库必须进版本控制。本轮恢复全靠编辑器快照 + transcript 拼出来，成本极高；
   **本次清理已 `git init` 并提交 `phase3-before_delete`，该缺口已补上。**
