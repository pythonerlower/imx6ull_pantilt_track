# 工程工作流

## 1. 开始前

先从当前计划、目标文件、直接调用关系和相关测试恢复最小上下文，不默认扫描或重写整个仓库。明确：

- Goal：本次必须得到的结果；
- Current / Expected：当前与期望行为；
- Non-goals：本次不处理的内容；
- Acceptance：可执行或可观察的验收标准。

## 2. 实施

按“小修改→局部验证→下一步”推进。修改前尽可能运行现有构建、测试或 smoke test；原有失败标记为 `PRE-EXISTING FAILURE`，不得归因于本次修改。

优先遵循现有实现和目录约定。新增依赖前确认标准库或现有依赖不能合理完成任务，并记录其部署和许可证影响。

### 2.1 就地改文件的安全边界（2026-10-07 事故，时刻警惕）

- **禁止** `open(f,"w").write(open(f).read()…)`。Python 先求值作为写入目标的
  `open(f,"w")`，文件在这一刻已被截断，右操作数读到的已是空串 —— **必然写空**。
- 就地改文件一律**写临时文件再 `os.replace()`**；或先 `cp f f.bak`，
  再用 `sed -i` 这类**先读后写**的工具。
- 跑突变测试或一次性验证脚本**之前**先落一份带时间戳的备份。
- 不得用"另一条长得像的命令是安全的"推断这条也安全 —— 安全的那条之所以安全，
  是因为它把读取提到了写入之前。**逐条看求值顺序。**
- 事后能靠 git 回退（仓库自 2026-10-07 `git init` 起已纳入版本控制，
  2026-10-08 已覆盖全部源码与文档），但**未提交的工作区改动照样一次写没**，
  所以这条边界不因有 git 而放宽。

**事故**：2026-10-07 14:13 用上述禁止写法验证一个突变体，把
`imx6ull_project_src/pc/tracker/main.py`（2305 行 / 115 KB，tracker 主程序）
清成 0 字节。当时仓库**尚未**纳入版本控制，恢复只能靠编辑器快照与会话记录拼接，
**无法逐字节还原**；经过、根因与恢复方式见
[`plan/phase3_status_20261007.md`](../plan/phase3_status_20261007.md) §8。
这条边界对应宪章第 6 条（保留契约和用户工作）。

## 3. 调试

执行以下闭环：

```text
观察证据 → 稳定复现 → 定位第一个错误状态
→ 单一根因假设 → 最小实验 → 结论
→ 最小修复 → 回归保护 → 重新验证
```

连续三次有依据的尝试仍失败时，停止叠加补丁，整理已排除方向，建立最小复现并重新建模。

## 4. 测试

验证真实行为而非私有实现。优先级按任务选择：单元/回归测试、集成测试、CLI 或协议测试、目标板 smoke test、人工可重复验收。硬件任务允许不用传统 TDD，但必须留下可执行验证步骤和观察信号。

性能结论必须有同环境基线、受控变量和重复测量；单次数据或局部加速不能代表端到端提升。

## 5. 审查

先检查需求符合性，再检查工程质量：

1. 是否遗漏验收项或越出范围；
2. correctness、回归、错误处理和边界；
3. 资源生命周期、并发和权限；
4. 可观测性、耦合、重复和复杂度；
5. diff 中是否混入临时日志、生成物或无关格式化。

## 6. 完成验证

最终修改后重新执行对应验证，读取退出码、标准输出、错误输出和产物，再逐项标记验收标准为 `VERIFIED`、`FAILED`、`UNVERIFIED` 或 `NOT APPLICABLE`。

若用户要求可运行交付，还必须验证目标环境的依赖、构建/安装、配置、启动、核心路径、日志和重复运行方式。构建成功不等于运行成功。

## 7. 记录

只保存支持恢复、解释和决策的内容：目标、命令、结果、关键配置、失败根因、限制和下一步。不得用大段终端输出或模板化日报代替结论。

## 8. 效率与成本节制

为高效快捷地开发，验证规模按当前问题裁剪，以节省 token 和时间：

- 不做长时间的、大数据量的、多类型的矩阵测试，也不对同一结论反复多次测试。一次有效验证足以支撑当前决策时就停止；确需更长时长、更大样本或更多组合时，先说明理由再执行。
- 不常驻在超时等待或空转中。会阻塞的调用必须带显式超时；没有新信息的轮询、重试和 sleep 不得循环进行。
- 测试参数取能回答问题的最小值（时长、帧数、尺寸、轮次），其上限以用户当前要求为准。

## 9. 上下文与 Token 控制

与第 8 节同属成本节制，区别是这里管**上下文**、那里管**验证规模**；与第 1 节互为表里（那里规定开始前怎么起手，这里规定全程不得回退到重扫描）。

- 优先复用当前对话中已确认的需求、架构和结论，不重复分析、扫描或检索已经明确的信息。
- 仅读取和修改当前任务直接相关的文件与代码；禁止无必要的全仓库扫描、无关重构和重复搜索。
- 测试遵循“最小充分验证”：只执行受本轮修改影响的编译、检查或测试，避免重复全量测试。第 2 节“修改前先跑一次现有构建/测试”是建立基线，不属于重复全量测试。
- 当前任务完成并验证通过后立即停止；非阻塞问题只记录，不自行扩展新的开发任务（与宪法第 5、9 条同一取向）。
