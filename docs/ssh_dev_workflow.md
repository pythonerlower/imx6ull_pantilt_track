# SSH 开发工作流

## 1. 目标

1. 直接在 Ubuntu 源端工作，不依赖 Samba 挂载写回。
2. 保证中文文档、脚本、代码在传输和落盘时保持 UTF-8 正确。
3. 每次修改都具备可验证、可回退、可复跑的闭环。

## 2. 适用范围

1. 代码阅读、文档修改、脚本运行、日志收集。
2. 内核模块构建、部置、`insmod/rmmod`、`dmesg`、`debugfs`、`ftrace`。
3. 板端验证脚本与复现实验。

## 3. 固定原则

1. 源文件路径以 Ubuntu 端为准，不以 Windows 盘符映射为准。
2. 中文内容不得通过不受控的 Windows shell 文本链路直接拼接后写入远端。
3. 文档与源码写入统一使用 UTF-8。
4. 每次修改前保留备份或确保可由 git 恢复。
5. 写回后必须立即回读验证，不通过则视为本轮修改失败。

## 4. 推荐工作流

### 4.1 连接阶段

1. 使用 SSH 登录 Ubuntu 源端。
2. 先确认当前用户、项目根目录与目标文件徔。
3. 只在项目源端路径下做修改。

### 4.2 读取阶段

1. 优先用 SSH/SFTP 直接读取远端文件。
2. 读取后先检查 UTF-8 解码是否正常。
3. 需要分析的片段尽量按段读取，不做大范围盲改。

### 4.3 修改阶段

1. 代码与英文内容可直接修改，但仍建议写后回读。
2. 中文文档必须使用 UTF-8 安全写入。
3. 写文件时优先采用“写临时文件 -> 原子替换”的方式，避免目标文件半写入。
4. 若目标文件属主不可直接覆盖，但目录可写，仍可通过临时文件替换完成更新。

### 4.4 验证阶段

1. 写回后立刻回读目标片段。
2. 检查中文是否出现 `?`、乱码或丢行。
3. 对代码文件再补充一次语义检查；对文档文件再补充一次段落结构检查。

### 4.5 回退阶段

1. 若写回内容异常，优先使甘本轮备份恢复。
2. 若是 git 管理文件，也可回到上一个已确认状态。
3. 未通过回读验证前，不进入下一步开发。

## 5. 文档修改专用规则

1. 修改中文 Markdown 时，先读取原文，再生成完整 UTF-8 文本后写回。
2. 不要把大量中文直接嵌入 Windows PowerShell 的长命令字符串后转发。
3. 若需要跨平台中转，优先传输 UTF-8 字节，不依赖本地代码页。
4. 修改完成后，至少回读标题、正文和文件尾部各一次。

## 6. 建议测试项

1. SSH 连接测试：确认可登录、可定位项目。
2. UTF-8 读取测试：确认中文文件读取正常。
3. 临时文件写入测试：写入含中文、英文、代码块的测试文件。
4. 原子替换测试：临时文件替换正式文件后内容不丢失。
5. 清理测试：测试文件与临时文件可正常删除。
