# Phase 3 执行计划：Pan/Tilt 控制 + 视频链路 + 自动目标跟踪

本文件是 [总计划](plan_imx6ull_pantilit_final.md) 第 Phase 3 章的展开，服从 `rules/` 全部规则。
总计划写于 2026-10-07 目录整改之前，本文件中的路径一律使用**整改后的现结构**。

## 0. 起点与协商结论

Phase 2 已交付（`config/pantilt_calibration.conf`：pan home=377 / 239..515，tilt home=242 / 162..342），
`pantilt_test` 已有 `probe/trial/nudge/calib/sweep`，但**缺** §3.1 要求的绝对定位命令。

2026-10-07 与用户协商后确定的 4 条边界：

| 项 | 结论 | 理由 |
| --- | --- | --- |
| PC 视觉依赖 | `pip install --user opencv-python numpy`（阿里云 HTTP 镜像） | OpenCV 只跑在 PC，板端零开销；避开 sudo 密码与系统 Python 污染，可 `pip uninstall` 撤销 |
| 板端视频链路 | **自研** V4L2 采集 + 板端 Ring Buffer + UDP 分包发送 | 计划 §3.3 要求环缓冲位于「V4L2 与发送之间」，既有 ffmpeg 链路是黑盒插不进去；UDP 而非 TCP，因 rules §4 禁止网络反向阻塞采集 |
| 正式控制接口 | `kernel/pantilt/` 内核字符驱动 `/dev/pantilt0` | rules §5 明确「再建立 `/dev/pantilt0` 正式接口；不得为展示效果跳过底层验证」 |
| 交付节奏 | 拆 3A/3B/3C/3D 四个里程碑，逐个板端验收 | rules「先单模块闭环、再系统集成」 |

**取舍说明**：计划 §3.3 同时写了「环形缓冲」与「复用现有已验证远程视频方案」，二者冲突——ffmpeg 内部缓冲无法暴露 frame_id/高水位/丢帧计数。本计划保留既有 ffmpeg UDP 链路**完整不动**作为回退与对照入口，新链路并行建立，不构成「提前删除已验证旧链路」。

## 1. 板端资源账

实测（2026-10-07）：**512 MB** DDR（available 310 MB）、**单核** Cortex-A7 @ 792 MHz、rootfs 余 5.8 G。

| 项 | 账 | 结论 |
| --- | --- | --- |
| 视频 Ring Buffer | 320×240 YUYV = 153,600 B/帧；6 槽 0.9 MB，8 槽 1.2 MB | 可忽略，**不为省内存缩槽位** |
| `pantilt.ko` + `pantilt_daemon` | 各数百 KB 量级 | 可忽略 |
| 裸 YUYV UDP 带宽 | 153,600×8 bit×15 fps ≈ **18.4 Mbps** | 直连 100 M 网口可承受；若丢包严重再上 MJPEG（板端有 `libjpeg.so.62`） |
| `/opt/QDesktop` | **89 MB RSS + 单核 10% CPU** | **单核才是真瓶颈**。3B 起测试期间建议停掉，收益大于任何选项取舍 |

停 QDesktop 会改变板端 LCD 界面，**属用户可见动作，执行前单独确认**，不默认做。

## 2. 总体数据流

```text
板端  OV5640 → V4L2 → Ring Buffer(N槽) → UDP 分包 ──┐
                                                     │ 视频 9200
PC    ‹──────────────────────────────────────────────┘
      │ 收帧重组 → get_target_center(frame) → error_x/error_y
      │ → deadband + P + 最大单步 → 绝对目标 tick
      ▼ 控制 9100（seq/timestamp/mode/pan/tilt）
板端  pantilt_daemon → 校验 seq/新鲜度/模式 → /dev/pantilt0
      │                                            │
      │                                      clamp + 限速渐进
      └── 遥测 9101（状态/当前 tick/限位次数/I2C 错误）──► PC 显示
```

职责边界（rules §1）：**PC 负责目标定位、误差计算、P 决策；板端只负责限位、限速和输出**。

## 3. 里程碑 3A —— 板端正式控制接口 `/dev/pantilt0`

**交付物**

```text
imx6ull_project_src/kernel/pantilt/
├── pantilt.c        misc 设备 + I2C + 限位/限速 + 看门狗 + debugfs
├── pantilt_uapi.h   与用户态共享的 ioctl ABI 定义（用户态用 -I 直接包含，不复制）
├── Makefile
└── README.md

imx6ull_project_src/user/pantilt_ctl/
├── pantilt_ctl.c    3A 验收 CLI：info / limit / target / home / stop
├── Makefile
└── README.md
```

验收工具不另起一个 `pantilt_test` 式的直写 I2C 程序，而是走 `/dev/pantilt0`：验收的对象就是这道接口本身，绕开它去验收没有意义。原有的 `pantilt_test` 保留为标定工具，并在会动舵机的子命令前加了 `/dev/pantilt0` 存在性检查（`probe` 只读、不受影响，可用 `PANTILT_ALLOW_CONFLICT=1` 强行并存）。

**接口**

```text
SET_LIMIT   pan/tilt 的 home、safe_min、safe_max、限速 slew_ms、看门狗 watchdog_ms
            （唯一会唤醒芯片并驱动舵机的调用；被认领后按 pantilt_state.conf 起步再爬回 home）
SET_TARGET  绝对目标 tick（双轴），驱动内 clamp + 限速渐进逼近
GET_STATE   当前 tick、目标 tick、home、限位、模式、限位次数、看门狗/I2C 计数、latency
HOME        缓慢回到 home
STOP        停止爬升并保持当前位置（不清输出，避免舵机失力掉落）
```

限速用 `slew_ms`（每 tick 多少毫秒）而不是 tick/s：与已验证的 `CALIB_RAMP_MS = 15 ms/tick` 同一量纲，代码里不必来回换算。`GET_STATE` 的 `last_latency_us` 记录 `delayed_work` 实际调度延迟，用来判断在多快的 slewing 下会丢步。

**驱动内行为**

- I2C：总线 1、地址 `0x40`，寄存器语义与 `pantilt_test.c` 一致（`MODE1=0x00`、`LED0_ON_L=0x06`、`PRESCALE=0xFE`、50 Hz → prescale 121）。
- **限位**：所有目标先 clamp 到 `[safe_min, safe_max]`，越界计数并记录最后一次越界值；`safe_min/safe_max` 由 daemon 从 `config/pantilt_calibration.conf` 经 `SET_LIMIT` 下发，**驱动不自己读配置文件**。
- **限速渐进**：定时器按固定 tick 步进逼近目标，步进间隔默认沿用已验证的 `CALIB_RAMP_MS = 15 ms/tick`（约 22–29 °/s）。**禁止启动或收到新目标时直接跳到该值**（rules §2 明确记录过首次试动突然大幅运动）。
- **看门狗**：`SET_TARGET` 超时未刷新 → 保持当前位置进入 HOLD（不是回 home，避免失控）。
- **状态准入**：`insmod` **不驱动舵机**。读回 `LEDn_ON/OFF` 判断芯片是否处于已知的 50 Hz 运行态；未知态一律拒绝动作，避免覆盖别的控制器正在输出的 PWM（沿用 `pantilt_test` 的准入思路）。
- **与 `pantilt_test` 互斥**：驱动在位时 `pantilt_test` 拒绝动作，反之亦然。
- **debugfs** `/sys/kernel/debug/pantilt/{state,limit,stats}`：为 Phase 6 §6.3 的 `command/limit/i2c error/update latency` 预留。

**验收（板端实测）**

| # | 项目 | 状态 |
| --- | --- | --- |
| 1 | `insmod` 后 `/dev/pantilt0` 存在，**舵机不动** | ✅ 2026-10-07 已实测 |
| 2 | 未认领时 `rmmod` 对硬件零写入 | ✅ 2026-10-07 已实测 |
| 3 | `debugfs` 三个只读入口可用 | ✅ 2026-10-07 已实测 |
| 4 | `pantilt_test` 与驱动互斥（动舵机类命令被拦） | ✅ 2026-10-07 已实测 |
| 5 | `insmod` 后内核日志为可读英文 | ✅ 2026-10-07 已实测 |
| 6 | `SET_LIMIT` 下发 `conf` 值后 `GET_STATE` 能原样读回 | ✅ 2026-10-07 已实测 |
| 7 | `HOME` 缓慢回 home，目视无跳变 | ✅ 2026-10-07 已实测 |
| 8 | 双轴小步 `SET_TARGET` 正常动作 | ✅ 2026-10-07 已实测 |
| 9 | 越界目标被 clamp 且计数递增 | ✅ 2026-10-07 已实测 |

第 6–10 项需操作者目视配合，2026-10-07 一次会话内逐项单独确认完成：全程 `i2c_err=0`、
`watchdog_trips=0`、无过冲、无堵转，`rmmod` 后芯片足迹与进模块前字节一致。完整记录见
`logs/phase3/20261007_3a_acceptance.md`。

唤醒前由操作者把两轴手动摆到标定 home 并写入板端 `pantilt_state.conf`（`0 377` / `1 242`），
使 `start == home`、爬回 home 为 0 步——这是唯一能保证「第一帧不跳变」的做法，
因为 `slew_ms` 只约束第二帧之后。

第 1、2 项的证据是同一条：完整 `rmmod` → `insmod` 一轮前后，`pantilt_test probe 1` 三次读回均为 `MODE1=0x91 MODE2=0x04 PRE_SCALE=0x1e`，字节一致。退出路径整体由 `d->initialized` 把关，从未 `SET_LIMIT` 时一个寄存器都不写。

**风险**：内核态 I2C 与 usleep/定时器上下文；`rmmod` 时若有定时器在跑必须完整回收。这是本阶段最容易出问题的一环，先做单轴小步、再双轴。第 6–10 项会真实驱动舵机，按 `rules/Hardware.md` 的要求逐项单独确认后再做，不连续跑。

## 4. 里程碑 3B —— daemon + 控制协议 + 视频/Ring Buffer

**交付物**

```text
imx6ull_project_src/user/pantilt_daemon/   协议、状态机、校验、看门狗
imx6ull_project_src/user/video_link/       V4L2 采集 + Ring Buffer + UDP 发送（板端）
imx6ull_project_src/pc/tracker/            收帧重组 + 手动控制客户端（PC 侧先起骨架）
docs/protocol.md                           协议冻结
```

**`pantilt_daemon`**

- 启动：**不认领**。要求驱动已是已认领状态（`status != UNINIT`），否则以退出码 3
  拒绝启动并提示先跑 `pantilt_ctl limit`；限位/当前姿态一律从 `GET_STATE` 回读，
  不再自己读 `pantilt_calibration.conf`。
  > 这是协商后的结论（冷启动策略 = 「默认拒绝，RUNNING 时回读接管」），
  > 与本文件早期写的「daemon 自己 SET_LIMIT → HOME」不同：`SET_LIMIT` 会唤醒
  > PCA9685 并让舵机真的开始转动，那必须是一次**有人确认的物理动作**，
  > 由带提示的 `pantilt_ctl limit` 做；daemon 在无人看守时"顺手代做"
  > 就会让云台自己动起来。
- 状态机第一版：`MANUAL / TRACK / LOST / HOLD / HOME`；第一版只需 `LOST → HOLD`（计划 §3.6）。
- **命令校验**：拒绝重复 `seq`、明显过期 `timestamp`、非法模式或越界值，并记录计数——这是 rules §4 的硬要求，不静默丢弃。
  另有一条自愈：`seq` 连续倒退超过 1 s 判定为「客户端换了一茬」并重置会话，
  否则 PC 重启后 daemon 会永久失聪。
- 看门狗：两层——daemon 侧 500 ms 断流 → `STOP`（兜「上位机没了」）；
  驱动侧 1500 ms → `HOLD`（兜「daemon 没了」），靠 20 Hz `KEEPALIVE` 续命。
- 遥测：20 Hz 回报当前 tick、目标、状态、限位次数、I2C 错误、各类拒绝计数。

**`video_link`（板端）**

- V4L2 采集 `/dev/video1`，320×240 YUYV 15 fps。
- 固定长度 Ring Buffer，槽数 `N ∈ [4, 8]` 可配，每帧记录 `frame_id / timestamp / size / slot`；满时覆盖最旧帧。
- 统计并暴露 `read_idx / write_idx / count / high_watermark / drop_overwrite_count`。
- 消费者经 UDP 分包发送；**采集永不因发送阻塞**（rules §4）。
- 摄像头偶发故障按既有统一策略：有序归还模块退出 → 重载重试（rules §8）。

**验收**：PC 能持续收帧且能重组；Ring Buffer 四项统计可读且丢帧时计数递增；控制命令能驱动云台手动动作；重复/过期命令被拒绝且计数可查。

三条**新增的设计约束**（写在这里，免得后面被"优化"掉）：

1. **收帧必须在独立线程**，且这是正确性而非性能：同线程时显示/检测一卡
   （建窗口、换尺寸）就没人收包，内核 rcvbuf（实测 416 KiB ≈ 0.19 s）溢出丢包，
   而**这种丢包连 `datagrams` 计数都看不到**。实测：60 fps 合成负载下整循环
   占 0.56 核，折算到 15 fps 约 0.14 核。
2. **`Target.error()` 没找到目标时返回 `None`，不是 `(0,0)`。** `(0,0)` 在 3D 里
   意味着"已经很准、别动"，与"看不见目标"是完全相反的结论。
3. **HUD 上的文案一律 ASCII。** `cv2.putText` 的 Hershey 字体没有 CJK 字形，
   中文画出来是看着像字、读不出来的乱码。中文留给终端（`Manual.note`），
   窗口用与它同步的 ASCII 短标签（`Manual.tag`），`display._ascii()` 兜底。

命令行（不加 `--video` 就是纯 3B 行为，一点没变）：

```bash
python3 main.py --host 192.168.137.50 --video --no-window \

python3 main.py --host 192.168.137.50 --video --hsv '<多段阈值>'    # 现场标定
```

### 3C 实机结果与阈值标定（2026-10-07）

**链路/叠加/状态字**：1542 帧完整、0 整帧丢失、0 重复/迟到，15 fps；
绿框/红点/红线/`err`/`TRACK` 全部出现在正确位置。

**检测缺陷：已定位并修复。** 当轮曾归因于形态学顺序（开→闭该改成闭→开），
**该结论已被实测否决**。用 735 帧干净原始数据重标后的真实根因是两条，互不替代：

| 缺陷 | 根因 | 修法 |
| --- | --- | --- |
| 676 帧真目标漏检 26 | 色相双区间中间 **[11,169] 是空的**；OV5640 的 AWB 漂移把红目标色相从 ~172 推到 160–168 | 第二段下界 **170 → 155** |
| 59 帧负样本误报 30 | `min_area=300` 在**噪声底之下**（木桌近端暖边稳定产出 194–372 px） | `min_area` **300 → 500** |

修后全量：**漏检 0/676、误报 3/59**；那 3 帧是目标出画后头 3 帧被静态红衣服顶替，
**已协商留给 3D 时域迟滞**（见本文 3D 一节）。

形态学**保持开→闭不动**——实测开运算中位损失仅 0.99、零帧损失超 50%，
且那两帧的掩膜在旧色相下**本来就是空的**（283 px / 166 px）。
完整证据、2×2 消融表、被否决的方案见

## 6. 里程碑 3D —— P 控制自动闭环

- `error_x = target_x - image_center_x`，`error_y = target_y - image_center_y`。
- 第一版控制律：`deadband + P + 最大单次步长 + 机械限位`。**不做 PID**（计划 §3.5、rules §3）。

云台左转时画面里的目标会**右移**，所以两者符号相反。这一条依旧只能实测，符号错了就是正反馈、上电即飞车。

**标定 Kp 时必须算进的两段固定延迟**（2026-10-07 新增，都是实测量出来的）：

1. **残帧成组延迟最坏约 200 ms。** `video_rx._emit_ready()` 是先来先交付：
   队头有一帧没结算，后面即使已经完整也不能跳过（跳了帧序就乱）。一帧缺片会把
   它后面最多 `window`(=3) 帧堵住，直到帧号滑出窗口才一起放行。
   15 fps、窗口 3 下最坏约 200 ms。这不是缺陷（真实链路上片丢 0.02%，
   出现频率很低），但它意味着**偶发的一大段陈旧画面**，而不是均匀的小延迟。
2. **检测 + 绘制约十几毫秒**（320×240 上实测整循环占 0.14 核 @15 fps）。

纸上算相位裕度时如果只算"采集 66 ms + 执行器"，会高估一大截。

**"若目标在中心附近来回荡，先减小 Kp、不要去调 `deadband`"——这条已被实测推翻，
不要照做。** 来回荡的根因不是增益太高，而是**机械回差**：1 tick 的输出变化会被回差
整段吃掉、画面不动，控制器于是继续喊，攒够了才跳一格、然后反向。**增益和死区都不在
这个环路上**，调它们只能改振荡的幅度与频率，消不掉它——处置见 §6.4。

本节关于"两段固定延迟必须算进 Kp 标定"的内容不受影响。

### 6.4 分度值附近的摆动：回差，以及 ROI 择优锁定（2026-10-07）

**现象**：只用 P + 中心点策略时，目标一旦被追上，舵机与目标点之间**始终存在
误差、一直摆动，定不下来**。

**根因：机械回差（丢失行程）在舵机死区之外，是叠在它上面的一层。**
量化执行器的极限环判据是 `Δu > Δb`（单步输出变化大于死区就一定绕不过去）。
但这里的门槛不是死区——1 tick 的输出变化会**先被回差整段吃掉**：画面不动，
控制器读到的误差就不变，于是每帧继续下发；积累到 H 格之后执行器才跳一格，
跳过头再反向。**闭环于是"喊了不动、攒够才跳"，摆动是结构性的，靠调
kp / deadband 都治不了**（它们不在这个环路上）。

**实测结论（2026-10-07 下午，2 分钟窗口实机验证）：H ≈ 4~7 tick。**
pan `--calib-lash` 三次给 6.7 / 6.2 / 4.2，tilt 给 6.9（后者台阶非单调、不可用）；
`--calib-sign --axis tilt` 单独量得 **+1.12 px/tick**（曾记 1.83）。
只有 H 变大能解释这个跌幅（`有效斜率 = 光学斜率 × (12−H)/12`）。
**探针本身在 H ≥ ~5 之后已经量不准**——每反向一步只动 ~1.1 px，低于检测噪声
`σ ≈ 1.0~1.6 px`，所以读数散成 4.2~6.9。要可信的 H 得调大 `LOAD_TICKS` / `MAX_BACK`
重跑，或直接量机械间隙。
详见 [`logs/phase3/20261007_lash_roi_acceptance.md`](../logs/phase3/20261007_lash_roi_acceptance.md) §3。

1 tick = 20 ms/4096 ≈ **4.883 µs ≈ 0.4395°**；MG90S 死带约 1.02 tick，
所以 H ≈ 4~7 tick 相当于**四到七个死带**，绝对绕不过去。
**另注：`--calib-sign` 掉到 1.12 px/tick 后，`--deadband` 默认 2.0 px 已经比一整格
分度值还大**（工具自己会印"死区必须小于 1.12 px"），默认值待重定。

**处置 A（机械侧，根治）**：把 H 从机械上消掉——舵盘螺丝、连杆旷量、舵机本身。
这一侧优先，因为它是唯一的根治手段。

**处置 B（算法侧，不改硬件的最小改造）——`--roi` + `--hold-window`：**
画面中心加一个圆形 ROI 半径；目标中心落进 ROI 后**不再连续追 0**，改为：
在 `--hold-window`（默认 2 s）内试若干个候选位姿，每个位姿取其 err 的
**中位数**，窗口结束锁到中位数最小的那个位姿上并保持。
保留摄像中心点用于跟踪校正，ROI 只负责判定"该不该择优、择优定在哪"。

> **必须按姿态取中位数，不能取瞬时最小** —— 瞬时最小是在噪声里挑最小值，等价于
> **挑噪声**（样本越多挑得越小，锁出来的位姿是随机的）；按姿态各取中位数再比，
> 比的才是"这个位姿稳不稳"，可复现。中位数样本噪声 `σ_med ≈ 1.25·σ_帧/√n`。

**`--calib-lash`：量回差的反向台阶探针。**
先把该轴朝一个方向走 12 tick 把该侧回差吃干净，再**反向**一次退 1 tick，
最多退 8 步，每步取 8 帧中位数。H 的估计**不是**"取第一个动了的那步"
（那是单点判断，`|k|≈2.3 px/步` 对 `σ≈0.8 px` 只有约 1.3σ，一次误判就报出
一个很自信的错数），而是对整条台阶做折线最小二乘
`d_i = k·max(0, i−H)`，H 在 201 点上搜索——**平的那一段同样带信息**。
理由：`H = i − d_i/k` 会把 k 的误差放大约 `d_i/k ≈ 5.6` 倍，单点法极其敏感。

- 与 `--calib-sign` 互斥（各占一趟标定），`--axis both` 被拒（两条轴的回差
  是两个数），`--lash-seconds` 为负被拒。
- `--calib-lash --auto` 时它当**前奏**（默认占 20 s），跑完整趟台阶约 6 s，
  到点把轴**放回起点**再交给闭环——两趟动作抢同一条轴，必须串行。
- **任何退出路径**（到点、异常、按 q、abort）都会归还轴。漏掉这条，云台会
  停在"起点 + 若干 tick"上而操作者以为"只是跑完了"——一个不报的位移。

**`--csv`：逐帧落盘。** 终端 HUD 是 2 秒一行，**分辨不出极限环的周期**，
判"为什么定不下来"非它不可。列含 err / 当前 tick / 下发目标 / 状态。
`--csv` 只在 `--auto` 下有内容、且必须配 `--video`，两条都在参数校验里拦掉——
否则会落一个只有表头的空文件，而操作者拿到它会以为"跑过了"。

**测试**：`test_auto.py` 用带丢失行程的对象（`LashPlant`，`out` 以

**实机验证（2026-10-07 下午，2 分钟窗口，静止目标，单轴两趟带 `--roi --csv --calib-lash`）：**

| | 结论 |

### 3B 视频链路实测（2026-10-07）

> **交接请看 [`phase3_status_20261007.md`](phase3_status_20261007.md)。**
> 那一份记的是本次排查的完整状态：宿主机 ICS 的根因与试错过程、**回滚锚点**、
> 环境陷阱清单、当前实测状态、未完成项。本节只保留与本计划直接相关的结论。

> **⚠ 本节的 `out=580` 是修好②之前那一轮的中间数据，已被后续验收取代。**
> **最终数是 `out=885`、PC 883 完整 / 2 残缺 / 0 整帧丢失，见
> [`logs/phase3/20261007_3b_video_acceptance.md`](../logs/phase3/20261007_3b_video_acceptance.md)。**
> 下面保留 580 那一轮的排查过程，因为它才是三个根因的发现现场。

**当时结果：板端 `out=580`，PC 收到 580 完整帧、0 整帧丢失、0 坏包，15.0 fps。**

但这个数是三个独立问题叠出来的，逐个说清楚，否则复现不了。

**① 链路有三倍帧复制（Windows 主机侧，不在本仓库内）。**
证据链：板端 `eth0` TX 包增量 **恰好等于** `video_link` 的 `sendto` 次数
（14300 == 14300），所以复制不在板端；PC 内核收到的唯一包数正好是 3 倍
（唯一 22550 → 收到 67382），且 100% 唯一交付、内核零错误。
成因（用户侧 Windows 诊断确认）：**ICS 的 IP 转发与 VMware 桥接（vmnet0）共用
同一块物理网卡**（Realtek USB GbE，`00:E0:4C:05:2C:88`），同一份上行包被
两条路径各送一次。直接后果是链路占用从 5.4× 余量掉到约 1.8×。
**这是宿主机配置问题，改它需要 Windows 侧操作，不在本仓库范围。**

**② PC 侧 CRC 是纯 Python 逐位循环——真正的阻塞点，已修。**
`ptproto.py` 的 `crc32()` 原来每包跑 11200 次解释器循环。环回基准（绕开物理
网络）显示：裸 `recvfrom` **56512 pkt/s** vs `VideoReceiver` **306 pkt/s**，
cProfile 里 `crc32` 占 `recv_frame` 总耗时的 **93.8%**（2407 µs/包）。
需求是 110 片 × 15 fps = **1650 pkt/s**——上限比需求低 5 倍，即 ①修好了也
还是收不到帧。换成 `zlib.crc32` 后 **20789 pkt/s**（12.6× 余量）。
等价性核对：355 组数据（含本文件自测向量）逐位一致；`proto_selftest.sh`
C↔Python 三份报文仍逐字节一致（`video` 向量的 CRC 字段就在被比较的字节里）。
细节见 [`docs/protocol.md`](../docs/protocol.md) §4.1。

**③ 已结算帧被迟到复制包"复活"，污染计数，已修。**
①的三份复制里，第三份常常在整帧交付完之后才到；当时的代码会把它当作"新帧"
重建槽位，随即被窗口判为残缺帧结算掉。实测形态：**板端只发了 580 帧，
接收端却报 580 完整 + 193 残缺**（`片丢 23.89%` 也是这么虚高出来的）。
这是**计数**错误，不是交付错误，肉眼审代码看不出来。
修法与回归测试见 [`docs/protocol.md`](../docs/protocol.md) §4。

**④ 未做、已知有边界的两项**（记在此处，别当成已解决）：
- `net.core.rmem_max` = 212992，实测拿到 425984 B ≈ 296 包 ≈ **0.18 s**。
  在 20789 pkt/s 的排空速率下暂时不是瓶颈，但 **3C 加 OpenCV 后若把显示/
  处理放进同一个收包线程，只要那边卡 200 ms 就会开始内核丢包**，而那种丢包
  连 `datagrams` 都看不到。3C 必须分线程。
- 批量收包（`recvmmsg`）没做。当前 12.6× 余量下不必做，留作 3D 之后的后手。

**⑤ `--fps` 不生效（已定位，未改）。**
`video_link --fps 5` 与 `--fps 15` 在板上**行为逐字节相同**，INFO 行都报
`帧率=15`，`fps_in` 都是 15.0。定位：`--fps` 只被送进 `VIDIOC_S_PARM`
（第 214–217 行），是**向传感器请求帧率**，不是输出限速；而驱动**接受**了这次
请求（没有 `[WARN] VIDIOC_S_PARM 失败`）却写回 `1/15`，即它不受理改帧率。
采集循环本身（`select` → `DQBUF` → `memcpy` → `QBUF`）**没有任何节流**，
来多少帧就发多少帧。所以 `--fps` 读起来像限速旋钮，实际只是传感器请求——
**改法待定，需先协商**（见下）。

### `--fps` 怎么改 —— A+B，2026-10-07 已实现并验收

| 方案 | 做什么 | 代价 |
|---|---|---|
| A 只改语义 | 帮助文本写明"向传感器请求帧率"，`actual_fps != cfg.fps` 时打印明确 WARN | 小、无行为风险；但降帧率的需求仍无解 |
| B 加发送侧限速 | `DQBUF` 后按目标间隔决定是否 `rb_push`（丢掉就不入队） | 才真正降低链路负载，正是应对①想要的能力；但会改变采集路径行为，且 3D 闭环的时序要重新对 |

**决定：A+B 一起做。** 把 `--fps` 重新定义成**输出目标帧率**（用户真正想要的
那个旋钮）：`DQBUF` 之后按目标间隔丢弃多余的帧，**丢弃的帧不进 Ring Buffer**；
同时把 `VIDIOC_S_PARM` 降级为"尽力而为"，不生效时打印明确 WARN 而不是沉默。

实施时必须连着做三件事，否则会踩坑：

1. `--fps` 的语义变了 → 帮助文本、`--stats` 里的 `fps_in/fps_out` 口径、
   以及**所有引用过这两个数的文档**（含 3B 验收记录）都要跟着改。
2. 采集路径被改了 → **3D 闭环的时序要重新对**，且 `FramePump` 的丢帧计数
   （`pump.dropped`）要能和板端主动丢的帧区分开，否则分不清"板端限速"
   和"PC 跟不上"。
3. 改完要重跑一次视频端到端验收（板端要重新编译部署）。

**实施结果（2026-10-07，PASS）**：板端 md5 `7e76ac40b5fed0958cdda33ed033d2e8`。
用**整数累加分频**（Bresenham）而不是"距上次推送够不够 1/fps 秒"——后者在目标≈
传感器帧率时会拍频，15 进 15 出实测掉到 7.5。`out_fps >= 传感器帧率` 时每帧放行，
所以默认值（15）是空操作。实测 `--fps 15/5/20` 三轮，`采集 = 节流丢 + 入环`
与 `入环 = 出环 + 覆盖丢 + 在环` 两条恒等式全部对上；`--fps 5` 把链路从
18.99 压到 6.39 Mbit/s。验收记录见
[`logs/phase3/20261007_fps_ab_acceptance.md`](../logs/phase3/20261007_fps_ab_acceptance.md)。

顺带修掉一个真 bug：S_PARM 被拒后无条件回读 `timeperframe` 会拿到**我们自己填的
请求值**，`--fps 20` 因此谎报"传感器 20 fps"（真值 30）并连锁判成"不节流"，
一路错得很安静。现在请求失败不回读，并加了一次实测采集率对账。
