# 开发收尾后的学习归档

这份文件回答一个很朴素的问题：**这块板子上的几个外设，到底是怎么把我坑了一遍的。**

它不记流水账，只留"现象 → 原因 → 以后怎么办"。每一条的最后都能收到同一句话上：
**数据手册和原理图描述的是"典型情况"，而你手上的是"这一块"。**

---

## 一、AP3216C（接近 + 环境光，走 I2C）

### 1.1 芯片说"我自己会判远近"——它不会

AP3216C 测接近度的原理很直白：红外 LED 打出去，看反射回来多少光，给一个 10 位的数值
（0 表示贴着，数值越大表示越远）。芯片内部还配了一对阈值寄存器，可以设成
"数值超出这个区间就报一次中断"。

听起来，"人靠近了"这件事芯片会自己告诉我。**但芯片给的那个"接近/远离"标志位在本板上
恒为 0。** 那个位就像小区门铃上写着"有人"的指示灯——灯是坏的，可门铃本身还在响。
能用的只有那个 10 位数值。

**结论**：远近必须自己拿数值比阈值判，别信标志位。工程里用的是一对阈值
（`low=20` / `high=80`），中间隔一段留作回差——不然人站在临界距离上，
状态会在"有人/没人"之间来回跳，像门被风吹得哗哗响。

同一颗芯片还有一个更阴的细节：`PSDATALOW` 这个字节里，**bit6 是"本帧数据无效"的标志、
bit7 是滞回模式下的状态位**，它们不是测量值的一部分。拼 10 位数值时如果直接
`(high<<8)|low`，这两个位就会混进去，读出来的数会莫名其妙地大。必须 `low & 0x0F`。

### 1.2 每次开机都得先"请前一位司机下车"

厂商 BSP 把 `ap3216c` 编译进了内核（builtin），开机时它就把 I2C 上的 `0-001e` 这个
地址绑走了。这时你再 `insmod` 自己写的 AP3216C 模块，是挤不进去的。

打个比方：**一个车位只能停一辆车**，厂商的车先停在那儿了。要么改设备树让它别停，
要么每次自己停车前先把它挪走：

```sh
echo 0-001e > /sys/bus/i2c/drivers/ap3216c/unbind
```

注意"每次"是真的每次——**板子一重启，BSP 就又绑回去了**，unbind 不会持久。
这是 Phase 4 和 Phase 6 都写进脚本前置步骤的硬约束。

### 1.3 为什么最后换成了 Linux Input 框架

老做法是每个应用程序自己去 `/sys` 里捞数值、自己判阈值，三个人写就有三套逻辑。
换成 Input 框架后，驱动负责判、应用只读 `/dev/input/eventX`，收到的是
`EV_SW` / `SW_FRONT_PROXIMITY` 这种语义化的事件——**"有人靠近了"变成一个事件，
而不是一个需要应用自己解释的数字**。这样上层（比如 Phase 6 的 `securityd`）
就不用再懂 AP3216C 的寄存器了。

## 二、ICM20608（六轴 IMU，走 SPI）

### 2.1 单位看错一格，阈值差 9.8 倍

这是我自己踩的最典型的一个坑。IIO 框架下，加速度的换算系数在
`in_accel_scale` 里。IIO 的**惯例**是 m/s²/LSB，我按惯例写：
`数值 × scale ÷ 9.80665 = 多少 g`。

可这颗芯片的驱动给的是 **g/LSB**：驱动源码注释里写得明明白白——
"以 ±2g 量程为例，4/2^16 = 0.000061035"。也就是说，量程除以 2 的 16 次方，
单位是 **g**。再除一次 9.80665，读数就**小了 9.8 倍**。

有点像把磅当成公斤：数字看着合理，实际差了一倍多。当时实测静止时读出 101 mg，
而物理上静止就是 1 g——101 这个数看着"像"噪声，其实是被缩小了 9.8 倍的真值。

**结论**：换算前先去驱动源码里确认 `scale` 的单位，别按框架惯例假设。

### 2.2 复位之后的第一口是"没站稳"的数

ICM20608 复位后第一次读出来的加速度是垃圾值。道理跟**刚开机就上体重秤**一样——
秤还没稳，读数是随机的。

做法很简单：初始化后 `sleep` 一下再读，或者读两次、丢掉第一个样本。工程里两种都用了。

### 2.3 中断脚：原理图上接了，板子上摸不到

这是 Phase 7 最大的一堵墙，也是"图纸 ≠ 实物"最干净的一个例子。

**图纸说接了**：核心板原理图上，ICM20608 的 `6D_INT` 确实连到了 `J2-22`，
也就是 `JTAG_MOD` = **GPIO1_IO10**（这个脚还跟 ATK 模块座的 `GBC_LED` 复用）。
驱动那边也没偷懒：它本来就配了 `INT_ENABLE = 0x01`（DATA_RDY 中断），
数据一准备好就往外打一个约 1 kHz、50 μs 的正脉冲。

**板子上却量不到**：把这个脚临时配成 GPIO 输入（带上拉），高速采了 5 万个样本，
**一次高电平都没有**；对应的 IRQ 号在中断计数里也是 **0 个边沿**。

所以这件事不是"寄存器没配对"，剩下的嫌疑在电气侧：要么这个复用网络被
`GBC_LED` / `SP_TX` 那边的负载拉住了，要么板子版本跟图纸有出入。
按计划定的门：**M1 不过，就不改设备树、不改驱动**——门守住了，
Phase 7 的振动检测改走**软件阈值**（自己轮询、自己比），而不是硬件中断。

### 2.4 测振动的判据，不是"加速度有多大"

决定走软件阈值之后，第一个冒出来的想法是：把三轴合起来算个**合矢量幅值** `|a|`，
超过某个值就算震了一下。

这个判据是坏的，原因很朴素：**静止的时候，`|a|` 恒等于 1 g**——因为重力本身就在那儿。
就像你想听清脚步声，却拿整个房间的总音量当判据：底噪一直在，脚步声淹在里面。

更糟的是它**方向不对称**：横向晃一下，`|a|` 只是二阶地涨一点点；轴向晃，`|a|` 反而
会**变小**，直接被漏掉。

**改成逐轴帧间差分**：拿这一次的三轴读数，减去上一次的三轴读数，取三个差里最大的那个
当"振动强度"。静止时它贴着 0（量化抖动量级），晃一下立刻跳起来——
这才是"变化量"，而不是"绝对值"。

顺带一个连锁结论：既然判据是**帧间**差分，**采样间隔就不能比振动本身还慢**。
原来 500 ms 轮一次，短促的一下就整个漏掉了；现在常速 100 ms，超过阈值后进 20 ms 的突发窗口。

## 三、PCA9685 + 双 MG90S（云台）

### 3.1 "I2C 有应答" ≠ "舵机会动"

第一次调试时，`/dev/i2c-1` 上 `0x40` 地址是有应答的，读 `MODE1` 得到 `0x11`。
看着一切正常，**可舵机一动不动**。

原因写在芯片手册里：`MODE1` 的 SLEEP 位是 1 —— 芯片还在**上电休眠**状态，
预分频也还是默认值。有应答只说明芯片活着，不代表它在输出 PWM。

这跟"看见灯亮着"不等于"机器在转"是一回事。**外设能通信，和它在干活，是两件事。**

### 3.2 关掉之前要先 RESTART

调完一轮之后把通道关掉、芯片休眠，再想唤醒，发现 `MODE1` 读出来是 `0x91` 而不是 `0x11`。
原因是 PCA9685 有个 RESTART 时序：从 SLEEP 里出来不能直接写，要按手册的顺序走一遍。
按手册改完，读回来就正常了。

**结论**：休眠/唤醒这类"状态迁移"必须照着手册的时序写，凭直觉开关会留下半死不活的状态。

### 3.3 限位是量出来的，不是算出来的

最初试动用的是"中心 307 tick ± 8"，能看见转，但**这不能当限位用**。
真正的机械端点是拿 `pantilt_test calib` 一点一点试出来的，最后写进
`config/pantilt_calibration.conf`：Pan 是 239..515、Tilt 是 162..342。

而且起点"直接跳到 307"这一步就太猛了——正式控制里姿态必须先确认，
再按固定周期小步逼近，不能一步跳过去。

## 四、OV5640（摄像头）

这个坑分两层，**要分开看，别混成一句"摄像头不稳定"**。

### 4.1 第一层：软件失败路径没清理干净（这是 bug）

延长线接法下，相机能过 I2C、`/dev/video1` 也在，但采集报
`VIDIOC_STREAMON: Timer expired`，内核说 `timeout when wait for SOF`
（SOF = Start Of Frame，等不到帧开始信号）。

真正致命的是**下一步**：旧的 `mx6s_capture` 在上一次启动失败后**没有归还 vb2 缓冲**，
再 `STREAMON` 一次时对空链表解引用，内核直接 Oops。

这跟"出门忘了关水龙头"类似：第一次失败本身可能只是小事，但**失败路径没打扫**，
第二次就会踩到上一滩水。在内核源码里补上失败时的缓冲归还和空链表检查后，
同样的延长线状态下连续两次**只报 SOF 超时、不再 Oops**。

### 4.2 第二层：接线/初始化的偶发问题（这不是 bug，是策略问题）

原生插接就正常。延长线正插有时行、有时第一次打开失败（`/dev/video1: Operation not permitted`），
重载一次又能跑。

最长的一次做到了 **662 秒连续 9936 帧、0 丢帧（跨了午夜）**，但那一轮的第 1 次尝试
就是失败的、第 2 次才通。所以准确的说法是：**延长线正插能连续采至少 11 分钟，
但重载后存在偶发的"首次打开失败"。**

据此定下的策略是**工程取舍，不是"修好了"**：出问题不硬撑，
**有序归还模块退出，再重载重试，默认最多 3 轮**；模块加载后静置 2 秒；
全部轮次都失败时按加载的反序 `rmmod` 再退出。这条策略现在是 `scripts/lib/camera_reload.sh`
和 `securityd` 的相机自愈逻辑。

> 报告里写 0 帧失败、和"重试后通过"，是两回事，不许混着说。

## 五、为什么检测算法不部署到 IMX6ULL 上

这一条不是排障记录，是一次**架构选择的存档**。写它是因为最容易出现的误读是
"板子算力不够所以只能放宿主机"——**这个说法不成立**，下面把它和真正的理由分开写。

### 板子跑得动

当前跟踪器的检测算法（HSV 颜色阈值 + 最大轮廓质心）在板端跑得动。
**不部署是架构选择**：板端只负责**采集、执行、安全**，算法侧整体留在宿主机。

| 项 | 2026-10-07 实测 |
| --- | --- |
| CPU | **单核** Cortex-A7 @ **792 MHz**（一直跑最高频） |
| 内存 | 492 MB 总 / 303 MB 可用 |
| 内核 | 4.1.15 |
| 编译器 | **无 gcc** —— 只能交叉编译 |
| python3 | 有，3.5.1 |
| `import cv2` / `import numpy` | **都失败**（无 python 扩展模块） |
| OpenCV 运行库 | 有**完整一套 3.1**（约 40 个 `.so`），厂商 rootfs 遗留 |
| OpenCV 头文件 | `/usr/include/opencv*` **不存在** |

板端还另有一条更便宜的路径：**摄像头出的是 YUYV，而 YUYV 本身就是 YCbCr**，
判红色只看 `Cr` 分量过阈值，**一次颜色空间转换都不用做**。而 `cvtColor`
恰恰是 OpenCV 那条路上最贵的一步。

### 那不选，是按重要性排的四条

1. **"在 Ubuntu 宿主机显示"是硬要求，帧无论如何都要过网。** 在板上再算一遍，
   省下的是板上的 CPU，不是带宽；而这份 CPU 要留给采集、执行和安全——
   单核上 `pantilt_daemon`(20 Hz) + `video_link`(15 fps) + `securityd` 已经同住一个核。
2. **真要压延迟，该搬的是整个闭环，不是只搬检测。** 实测 PC 侧这段成组延迟最坏约
   **200 ms**（`video_rx._emit_ready()` 先来先交付，一帧缺片会把它后面最多 3 帧堵住）。
   只把检测搬到板上，反而变成"帧到板、结果回 PC"，多一跳。
3. **板端背上算法，改参成本从"改命令行"变成"交叉编译 + 部署 + 重启进程"。**
   阈值本来就是要现场标的（`--hsv` / `--min-area`）。
4. **算法复杂度只会往上走。** 当前是像素阈值；再往上一档就是需要模型推理的识别类任务，
   那类推理在单核 A7 上没有实时性可言（库在、头文件不在；就算补齐也算不动）。
   与其把"阈值能跑"这条线固化在板端，不如一开始就让板端的定位
   （采集 + 执行 + 安全）**不随算法演进而改**。

### 哪天该反过来

- 网络断了也要能跟踪（板端自治）
- 宿主机不在环里（脱机演示）
- 那 200 ms 成为控制品质的瓶颈，且只想改一端

这三条现在都不成立。**不选 ≠ 不可行**——条件变了就该重估，上面三条是重估的入口。

### 留给重估用的数字

- 板端 memcpy 进环缓冲 **0.34~0.35 ms/帧**（320×240，M6 实测）
- 链路实测 **18.99 Mbit/s** @320×240 YUYV/15 fps；`--fps 5` 降到 **6.39 Mbit/s**
- PC 侧 x86 桌面核（3C 实测，60 fps 折算到 15 fps）：只收帧 ~5%、+检测 ~11%、
  +绘制完整循环 ~14% —— 即**检测本身约占桌面核 6%**

> **板端的检测耗时没有实测过。** 从"桌面核 6%"外推到 A7 的误差带横跨一个数量级：
> 桌面用 AVX2、乱序四发射；A7 是顺序双发射 + 只有 NEON，主频还低 4 倍多。
> 乐观 3 倍 → 约 18 fps 够用；悲观 20 倍 → 约 5.6 fps 不够。
> **这条只有实测能定，本文件不含该数据。**

## 收尾：这几件事是同一件事

| 哪个外设 | 手册/图纸说的 | 板子上实际的 | 该怎么办 |
| --- | --- | --- | --- |
| AP3216C | 有"接近"标志位 | 恒为 0 | 自己拿数值比阈值 |
| ICM20608 | IIO 惯例是 m/s² | 驱动给的是 g | 换算前先查单位 |
| ICM20608 | INT 脚接了 | 5 万样本 0 个边沿 | 放弃中断，走软件阈值 |
| PCA9685 | I2C 有应答 | 芯片还在 SLEEP | 通信正常 ≠ 在干活 |
| OV5640 | 出帧就行 | 失败后不归还缓冲 → Oops | 失败路径也要打扫 |

**共同的一条**：手册写的是"典型情况"，你的板子上是"这一块"。
凡是**拿外设数据做判断**的地方——阈值、单位、标志位、中断脚——都要先量一遍再写代码。
量一遍的成本，比事后把 9.8 倍的误差当成"噪声底"去调参数，低得多。
